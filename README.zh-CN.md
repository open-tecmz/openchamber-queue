# OpenChamber 队列

**给 [OpenChamber](https://openchamber.dev) 的按项目任务队列扩展。**
添加任务、打开开关，项目空闲满队列设定的等待时间（默认 30 秒，可按项目调整）后，下一个任务就会自动开始运行 —— 一次一个，无需逐个点击。

一条任务由两部分组成：**内容**（提示词）和附带的图片。模型、agent 等使用项目自身的默认
选择。该项目按队列设定的等待时间（默认 30 秒）保持空闲后，任务才会开始，因此没有任务时侧栏保持安静。

> 这是一个 OpenChamber **扩展**（面板 + 本地服务），不是 OpenCode 插件。

## 功能

- **每个项目一条队列** —— 切换项目即切换队列。
- **图片随任务一起走** —— 可以直接粘贴截图、把图片拖到面板上，或点「添加图片」选择文件；任务会带上它，下发的新会话在第一条提示词里就能看到这张图。
- **自动下发** —— 项目空闲满队列设定的等待时间（默认 30 秒）后自动建会话、发内容，无需逐个点击。
- **按项目配置调度** —— 面板里可以用秒为单位调整「空闲等待」和「提问后等待」，并选择什么算「忙碌」：等待提问回答、等待权限确认、后台命令仍在运行、或项目里的其它会话是否占住队列。这些设置随队列保存在 `state.json`。
- **立即执行** —— 第二个按钮不排队，直接用输入内容创建新会话并发送。
- **追加到当前会话** —— 第三个按钮把输入内容入队并记下当前打开的会话 ID；等项目空闲后，队列把提示词发送到该会话，而不是新建一个。
- **单条任务立即运行** —— 每行都有 *执行* 按钮，可立即用该条任务创建会话并把它移出队列，计入「已完成」。
- **单条任务开关** —— 每行操作栏末尾有一个 *启用* 复选框：关掉的任务保留在队列中的位置，但自动调度会跳过它；手动点 *执行* 仍可运行。「新任务」这一行也有同样的复选框，用来决定之后新加入的任务是否默认启用（默认勾选），入队后仍可逐条切换。
- **三行摘要** —— 每条任务的内容以最多三行的摘要显示（保留原有换行），较长的提示词不打开编辑器也能看清。
- **防失控保护** —— 会话以 `failed` 状态结束，或创建会话 / 发送提示词失败，都算一次异常；连续几次异常会先暂停队列，避免继续消耗任务。
- **提交即出队** —— 任务创建会话后立即从队列移除并计入「已完成」；失败的运行不会把任务放回队列。队列空了会自动关闭开关。
- **询问不阻塞** —— 等待提问的会话不占用项目，下一个任务仍会下发，但会多等 5 分钟，先给你留出回答的时间。
- **停止时可编辑** —— 点击任务卡片即可就地编辑；队列运行中会拒绝修改。
- **关页面也能工作** —— 由服务器端本地服务驱动，不依赖浏览器标签页。
- **输入不丢** —— 输入框内容（含图片）按项目保存为草稿并写入本地服务，刷新、重启 OpenChamber 或意外退出后都会恢复；后台队列变化不会清空正在输入的任务。
- **面板多语言** —— 跟随 OpenChamber 语言（英文、简体中文、繁體中文）。

## 工作原理

### 调度规则

对每个项目，每次检查：

1. 队列未启用或为空 → 不动作。
2. 队列自己启动的会话仍在**执行** → 等待。
3. 项目里**其它**会话真正在执行 → 等待。
4. 项目还必须保持队列设定的**空闲等待**（默认 30 秒，可在面板的调度设置里按项目调整）。
   这段时间内只要有会话被激活（你自己开的会话、刚结束的会话又重试等），就重新计时，让项目
   有时间平静下来。如果上一个任务结束时**停在提问上**，则改为等待队列设定的**提问后等待**
   （默认 5 分钟），先给你留出回答的时间。
5. 取队首**仍处于启用状态**的待执行任务 → 创建会话 → 发送内容；被停用的任务保留原位、被跳过，
   由它后面的启用任务先跑。任务随即离开队列并计入「已完成」。下一个任务前同样重新等待。
6. 该会话不再执行（空闲、消失或正在提问）后项目恢复空闲，重新计时；队列清空后自动关闭开关。

这一次等待对第一个任务同样生效：打开开关时若有任务在等，会等过一个空闲等待后才开始，而不是立即开始。

不带图片的任务只走一次调用：控制 API 建好会话并发送提示词，顺带应用项目的默认模型。带图片的
任务走不了这条路（该调用只收文本），因此先建会话，再把项目默认的模型和 agent 切换上去，然后用
会话自己的路由发送提示词——每张图片一个 file part，内容以 data URL 携带，与应用自带输入框的
发送路径一致。**追加**任务则完全跳过建会话这一步：提示词（带图片时走同样的路由）直接发往它
记录的会话 ID，该会话保留自己的模型、agent 和历史。

「真正在执行」指 `running`、`retrying`、`waiting-permission`；`waiting-question`
默认**不算占用**。所以智能体提问不会卡住队列（其任务早已提交，下一个任务只是会多等过提问后
等待），而你自己开的会话会让队列排队等待。后台子智能体是独立的子会话：父会话在启动它的那一刻
就空闲了，但队列会一直跟到子会话真正结束（含嵌套的子会话），不会把任务当成已完成。后台命令
则不同——OpenCode 不记录它是测试还是服务，所以一小时的测试和忘记关的开发服务看起来一样。这个
等待因此有上限：超过「后台命令最长等待」（默认 2 小时，按项目配置；填 0 表示一直等待）后就把
这段暂停视为空闲。会话本身仍在观察中，如果命令之后真的结束并唤醒它，项目会重新算作忙碌。

调度设置把这些默认行为变成按项目的选择。在「以下情况算作忙碌」里，「正在等待提问回答」默认
不勾选，其余三项默认勾选。勾上「正在等待提问回答」后，会话会一直保持运行中直到你回答，而不是
等过提问后等待就把下一个任务放出来；取消「正在等待权限确认」或「正在运行后台命令」会把对应的
暂停视为空闲；取消「其它会话正在活动」则允许队列在你同项目里手动工作时也继续下发。`running`
和 `retrying` 始终算忙碌。

### 防失控保护

「下发成功」不等于「这一轮执行成功」。模型接口挂掉、额度用尽或密钥失效时，会话会以失败状态结束；
如果没有保护，普通的空闲等待会让队列继续下发，把上百条任务一条条消耗掉。

OpenCode 会在每一轮结束时写一条 `type: "idle"` 的记录，带 `outcome`：`succeeded`（正常结束）、
`failed`（请求失败，带 `error.type`，例如 `provider.transport`）或 `interrupted`（手动停止或
OpenCode 重启）。会话空闲后，队列通过与应用相同的会话代理路由读取这条记录，再判定这一轮：

- **succeeded** —— 正常结束；同时把连续失败次数清零。
- **failed** —— 真正的请求失败（连接中断、超时、鉴权、额度、模型不存在等）；计一次失败，并保留错误信息给面板。
- **interrupted** —— 既不算成功也不算失败，次数保持不变。

连续 **2 次失败**（默认，按项目配置）后，队列自动关掉开关，剩余任务一条不动。面板顶部显示
最后一次错误和「立即继续」；只有你手动恢复队列才会重新开始，所以模型坏掉时不会在你离开时
把队列清空。创建会话或发送提示词就失败也按同样方式计数，那条任务会留在队列里标为失败。

失败的那一轮任务**不会放回队列**：它在提交时就已经出队，队列也没有保留提示词副本可以重试；
请到 OpenChamber 的会话里查看历史。把「连续异常次数」设为 0 即关闭熔断。

正常但很快返回的回答也是 `succeeded`，不会被误判；工具命令返回非 0 属于某一轮工作的一部分，
也不算一次失败。

### 后台服务

队列由宿主为 `contributes.service` 启动的 Node 进程拥有。它调用本机 OpenChamber
控制 API（与自带 `openchamber` CLI 同一条路）读取会话状态、创建会话、发送提示词，
即使没有面板或窗口打开也持续运行。

面板只是这个服务的视图，**不会**再维护一份自己的队列副本。服务尚未就绪时，面板显示
「连接中」并自动重试。因此，在服务启动过程中加入的任务不会被写进服务看不到的存储里，
要么送达服务，要么面板仍在提示连接中。

本地服务必须在安装时批准，没有它队列无法工作；批准它，队列才能在后台持续运行。

## 安装

需要 OpenChamber **2.0.0 或更高**（网页版或桌面版）。

1. **设置 → 扩展**。
2. 在 **文件夹、ZIP 或 URL** 中粘贴以下之一并点击 **添加**：
   - 最新打包的 zip —— 下面的地址始终指向最新构建：
     `https://github.com/open-tecmz/openchamber-queue/releases/latest/download/openchamber-queue-latest.zip`
   - 最新 **Releases** 页面上的 `.zip` 文件；
   - 本地克隆的 `dist/` 目录（先执行一次 `npm run build`）；
   - `release` 分支的 git 地址 ——
     `https://github.com/open-tecmz/openchamber-queue.git#release`
     （git 安装可在 设置 → 扩展 中 **更新**，依据 `package.json` 版本号升高；
     zip 安装不支持应用内更新，需手动重新添加更新的 zip）。
3. 在权限对话框中点击 **允许并启用**。它会列出 `prompt`、`sessions`、`service`；
   本地服务以你的完整用户权限运行。

## 使用

在侧栏扩展区打开 **队列** 面板：

1. 在输入框里填写任务 → **立即执行** 直接创建新会话，**加入队列** 排队等待，或
   **追加到会话** 把它排进当前打开的会话。
2. 可选：最多附 4 张图片——直接粘贴截图、把图片拖到面板上，或点 **添加图片** 选择文件。
   它们随任务一起走，会在新会话的第一条提示词里作为图片发出。任务必须有文字，图片只是随行。
3. 打开 **启用队列** 开关。
4. 之后无需干预。项目空闲满队列设定的等待时间（默认 30 秒）后队首任务开跑，跑完自动接下一个。

顶栏显示当前模式，右上角是两个计数：**待执行 / 已完成**。每行以三行摘要显示任务内容，并带有
*执行*、*置顶*、*重试*（仅失败时）、*删除*、末尾的 *启用* 复选框，以及该任务带了几张图片；
*执行* 会立即用该条任务创建会话并移出队列，不必等项目空闲。*启用* 复选框是这条任务自己的自动
调度开关：取消勾选后调度器会跳过它并保留其原位，手动 *执行* 仍然可用。「新任务」这一行也有
同样的复选框，决定之后新加入的任务是否默认启用（默认勾选），因此可以先批量入队、再逐条开启。
队列停止时，点击某一行会展开为编辑器，带 **保存** / **取消**——在那里可以改文字，也可以点图片
上的 × 把它去掉。

其它入队方式：

- 消息菜单 → **加入队列**（把该条消息内容入队）；
- 聊天框斜杠命令 → `/queue <内容>`。

**调度设置**位于队列开关下方，默认收起，标题行会显示当前生效的值（默认「空闲 30 秒 ·
提问后 5 分钟」）。展开后可以用秒设置空闲等待和提问后等待，并勾选哪些情况算「忙碌」：
「正在等待提问回答」「正在等待权限确认」「正在运行后台命令」「其它会话正在活动」。同一个面板里
还有**防失控保护**：*连续异常次数*（默认 2 次，按项目配置；填 0 关闭熔断）和*后台命令最长等待*
（默认 2 小时；填 0 表示一直等待）。每次修改都会直接写入队列服务：勾选项立即生效，数字则在
按回车或输入框失焦时生效，避免把输入到一半的值存下去；
超出范围的值会被拒绝。保存成功会弹出提示，失败会显示原因。设置按项目保存，随队列写入
`state.json`。

## 存储与持久化

| 数据 | 位置 |
| --- | --- |
| 队列数据 | `~/.config/openchamber-queue/state.json`，或 `$OPENCHAMBER_QUEUE_DATA_DIR/state.json` |
| 附件图片 | `~/.config/openchamber-queue/images/<id>`（另有 `<id>.thumb` 缩略图） |
| 运行日志 | `~/.config/openchamber-queue/logs/service.log`，或 `$OPENCHAMBER_QUEUE_LOG_DIR/service.log` |
| 安装记录与权限 | `<OpenChamber 数据目录>/extensions.json` |

队列把状态文件单独放在宿主数据目录**旁边**，绝不放进任何项目目录里。宿主数据目录为
`~/.config/openchamber`，除非宿主侧设置了 `OPENCHAMBER_DATA_DIR`（该变量不会传给 service
进程，因此自定义的宿主数据目录不会被镜像过来）。

后台服务把运行过程写入 `logs/service.log`，这是排查派发或会话异常时最先要看的文件。
当前文件写到 10 MB 就滚动一次，旁边保留 5 份带时间戳的备份，日志目录不会无限增长。

图片在「附加」的那一刻就写入 store，任务里只存名字、类型和大小——图片字节**不会**进入
`state.json`。不再被任何任务或草稿引用的图片（任务被删、输入框被清空）会在十分钟后由服务的
清理过程删除，目录不会无限增长。

数据是普通 JSON 文件，**重启、升级、卸载都不会丢**。每个项目的输入框草稿（含图片）也保存在
同一个文件里，刷新或重启后会自动恢复。但**后台 worker 不会自动启动**：
OpenChamber 只在有请求时才拉起扩展服务，因此 OpenChamber 进程重启后，队列会暂停，
直到你打开一次面板（或触发一次消息动作 / `/queue` 命令）。之后它会常驻，原先已启用的
队列会从断点继续。

卸载扩展会清除安装记录与权限；要一并清空队列数据，请手动删除
`~/.config/openchamber-queue/`。

## 权限

| 权限 | 用途 |
| --- | --- |
| `sessions` | 列出项目与会话、创建会话 |
| `prompt` | 把任务内容发送到新会话 |
| `service` | 拥有队列的本地服务；必需，且以你的完整用户权限运行 |

队列没有面板内的回退模式：若本地服务未获批准，面板会一直停留在连接中状态。

## 已知限制

- **冷启动** —— 见上文：每次 OpenChamber 进程启动后，需要一次打开面板（或动作）
  才能把后台 worker 唤醒。
- **非公开接口** —— 服务使用产品自身的控制 API 与代理的 OpenCode 会话路由。这些接口
  自带的 CLI 也在用，但不是面向扩展的公开契约，版本升级可能变动。
- **图片** —— 每个任务最多 4 张、每张 5 MB，且只有能读图的模型才用得上。带图片的任务
  无法沿用控制 API 自己的默认解析，因此服务会从 OpenChamber 设置里读出项目默认的模型与
  agent 并切换到该会话上；两者都没配置时，就交给 OpenCode 自己的默认值。
- **任务在提交时即计为完成** —— 队列只负责发出提示词，无法判断智能体做出来的东西对不对。
  熔断能抓住「会话以失败状态结束」的情况；正常结束但结果不对，仍然只能到会话里看。失败那一轮
  的任务不会放回队列。
- **结束状态来自会话的 `idle` 记录** —— 通过代理的会话路由读取。如果读取失败，这一轮按
  「未知」处理、不计数，所以读取故障本身不会误停队列。
- **清单字符串无法本地化** —— 扩展 API 的面板名、命令描述、动作标签是固定字符串，
  它们保持声明语言；面板内部则跟随 OpenChamber 语言。
- 扩展不会在 VS Code 与移动端加载，队列同样不可用。

## 开发

```bash
npm install
npm run build       # 组装可安装包到 dist/
npm run typecheck
npm test            # 先构建，再针对 stub OpenChamber 跑隔离端到端测试
```

`npm run build` 会把整个可安装包写入 `dist/`：`dist/package.json`、`dist/icon.svg`、
`dist/panel/{index,background}.html`，以及两个产物 `dist/panel/main.js`（浏览器 IIFE）
与 `dist/service/main.js`（Node ESM）。宿主按包内路径直接加载已构建的 `.js`，因此页面与
其 bundle 必须位于同一目录。`dist/` 是生成物，**不提交**；CI 在每次推送到 `main` 时构建它。

开发时把 `dist/` 作为文件夹安装（设置 → 扩展）：它直接读取你的目录，改完重建即可刷新。
`npm test` 覆盖后台服务。

宿主不会编译扩展：只发布已构建文件。新增语言只需改 `src/i18n.ts` 并重新构建。这里只使用
`devDependencies`，仓库不包含 `node_modules`。每次改动都要在 `changelog.md` 中记录
（规范见 `AGENTS.md`）。

## 语言

面板跟随 OpenChamber 语言，找不到时回退英文。面板文案已内置 `en`、`zh-cn`、`zh-tw`；
在 `src/i18n.ts` 的 `DICTIONARIES` 中新增一份即可，字典类型会让缺失的键在编译期报错。
文档提供英文（[README.md](./README.md)）与简体中文（本文件）。
